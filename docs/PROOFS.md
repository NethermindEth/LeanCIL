# Writing checked proofs

Certificate validation streams fallthrough states and uses balanced indexes for branch
destinations. `FeatureFlowValid_iff_list` and `ScalarFlowValid_iff_list` recover the original
list-indexed rules without changing their entry, reachability, opcode or bounds requirements.
`foldEntry` takes the optional lookup result, so a list-based caller writes
`foldEntry roles[target]?`. Missing entries retain the original permissive fold-role result;
the successor-state check independently rejects a target missing from its certificate.

Division intrinsic validation classifies each emitted intrinsic once and removes the common
assembly scope once when recognizing a raw call's family. Its signature-byte table is generated
from the existing signature strings at elaboration time; a kernel-checked equality proves the
table exact without adding axioms. `DivisionIntrinsicsValid_iff_original` proves equivalence to
the original signature lookup, malformed-family rejection, arity, reachability, profile
availability and length checks for arbitrary raw metadata, including non-ASCII identities.

Feature getter validation likewise checks the common assembly/type prefix once, then compares
literal UTF-8 suffixes. `featureGetter_eq_original` proves equality with the original lookup
for every raw call site; a separate kernel-checked equality validates the generated suffix
table. Prefix truncation, trailing bytes, non-ASCII names and call-shape mismatches remain
rejected. This changes certificate checking cost, not the admitted feature getters.

Generated managed-call certificates use `cil_managed_calls` to prove the unchanged
`ManagedCallsValid` proposition. The tactic unfolds the supplied generated definitions and
proves identical scoped types and generic arguments by reflexivity. Remaining checks use
kernel decision; unsupported proof shapes fall back to the original complete decision.
The validator still checks targets, method tokens, type arguments, exact parameter and return
types, instance metadata, reachability and argument counts. This changes proof construction;
source binding, certificate audits and kernel replay are unchanged.

Generated primitive and generic-constructor types reference `Extraction.runtimeScope` only
when their full assembly identity matches it exactly. Its materialized UTF-8 bytes are
definitionally equal to the original string, as proved by `runtimeScope_eq`. Version, culture
and public-key token remain part of the identity; all other scopes retain their literal values.
This representation avoids decoding the same string during each certificate decision.

Each distinct reachable external-call identity similarly receives one generated byte constant.
Its `Bytes_eq` theorem proves exact equality with the original full string's UTF-8 bytes by
reflexivity. The string's UTF-8 validity proof and its equality theorem reuse that checked
equality; neither introduces axioms. Repeated occurrences of an identical target, including
across original and specialized metadata, share the constant. Validators still parse and
compare the full identity, including assembly version, culture, public-key token, declaring
type, method and signature. Pruned-only calls
retain literals, and call-free extractions emit no additional declarations. This changes data
representation, not scalar, division, specialization or admission rules.

Use `CIL.Safety.invoke` for specifications that include checked memory execution.
State the mathematical contract and its input/memory preconditions independently
of the implementation. The [soundness boundary](SOUNDNESS.md) describes what a
successful checked execution establishes.

## Compose instructions

Import `CIL.Safety.SymbolicExecution` and mark definitions used for instruction
lookup with `@[cil_code]`. This complete example executes eight instructions on
symbolic inputs and preserves arbitrary caller memory:

```lean
import CIL.Safety.SymbolicExecution

namespace ProofGuide

@[cil_code] def arithmeticMethod : CIL.Method := {
  code := [.arg 0, .arg 1, .const32 1, .shl, .add, .const32 0, .gtu, .ret]
  locals := [], returnsValue := true }

theorem checked_arithmetic (memory : CIL.Safety.Memory) (left right : CIL.W32) :
    CIL.Safety.invoke [arithmeticMethod] 9 0
      [.scalar (.i32 left), .scalar (.i32 right)] memory =
      .ok (memory, [.scalar (.i32 (if left + (right <<< 1) > 0 then 1 else 0))]) := by
  cil_checked_steps

end ProofGuide
```

The [automation regression](../Tests/Automation.lean) checks this pattern and
symbolic branch proofs. This handwritten body demonstrates the tactic; a proof
about an assembly must bind its body to the generated program, as described in
in [Bind bodies to the extraction](#bind-bodies-to-the-extraction), and pass verification.

`cil_checked_steps` composes `invoke_of_run`, `run_next`, `run_return` and
`run_call_of_invoke`. It checks method/instruction lookups and frame setup,
infers intermediate states, and checks the returned values. These lemmas are
also available directly from [StepComposition](../CIL/Safety/StepComposition.lean)
and [CallComposition](../CIL/Safety/CallComposition.lean) for manual proofs.

At a return, the tactic leaves the equation between the computed checked result
and the stated result as a proof goal. It closes that equation automatically
only when `with_reducible rfl` succeeds after frame cleanup, list normalization
and literal shift-count reduction. Cleanup also drops the narrowing of an
`if p then 1 else 0` result, so a narrow Boolean return needs no unfolding of
`NarrowKind.extend`. A follow-up `simp [leaveFrame, NarrowKind.extend]; split <;> rfl`
after such a return now fails with "no goals" and must be deleted. Other
mathematical results can need a separate `simp` or case split. The remaining goal contains the returned values, rather than an
unexecuted `run`. `cil_contract_steps` likewise leaves the return postcondition
as a goal.

A run-to-run goal `run p (fuel + n) m 0 .. = run p fuel m n ..` closes with
`cil_checked_steps` when the stepped state is syntactically the target: symbolic
`fuel` stops stepping there. With literal fuel and a target equal only up to
rewriting, `cil_checked_steps n [facts]` takes exactly `n` steps and leaves the
residual `run` equation. A call counts as one step: the callee runs to its
return and the residual starts at the caller's next instruction.
Unlike `cil_contract_steps n`, which takes at most `n` steps and stops silently
when one fails, it errors unless all `n` steps are taken, since a residual at the
wrong pc would not match the target.
`MemoryBelow.frame_round_trip` carries caller memory across `enterFrame` and
`leaveFrame` when the callee body keeps it.

The single-step helper, `cil_checked_step [facts]`, first tries each supplied
step fact for the fetched opcode: a fact whose conclusion is
`step body op pc args frame stack memory = result`, given as a hypothesis, a
lemma, or an applied term such as `store value`. It is applied at
reducible-and-instances transparency, then retried with the `@[cil_code]`
definitions in its type unfolded, so a fact stated on the named body matches both
a body reached through a lookup hypothesis and the literal body that an extracted
program's lookup produces. Otherwise the helper selects
its closing strategy from the opcode. Pure scalar operations try `rfl` even when
facts are supplied. Memory operations, local operations, instruction-dispatcher
arms and branches use `cil_step` equations and the supplied facts. This keeps
memory results in the form named by their facts, and resolves branch conditions
before choosing the next program counter. Unknown opcode heads use the equation path.

Intrinsic steps expose `checkedIntrinsic` and apply proved `@[cil_eval]` lemmas
before unfolding the intrinsic evaluator. Register consumer lemmas in the form
`CIL.evalIntrinsic operation operands = some result`. Nonnegative `BitVec.ofInt`
literals become `BitVec.ofNat` literals so these equations can match, so state
`@[cil_eval]` lemmas with `BitVec.ofNat` operands. A supplied evaluation fact may
instead use a numeral operand, such as `.i32 27`: when one is supplied, a second
pass respells literal `BitVec.ofNat n k` operands as numerals and leaves symbolic
`BitVec.ofNat n x` values unchanged. The tactic keeps the lemma's result form. It then removes literal stack `take`, `drop`,
`reverse` and append expressions before the next step. These rewrites do not
simplify consumer arithmetic or unfold consumer value definitions.

Value-only ops also have one equation per i32/i64 operand shape, generated by
`cil_value_steps` when the library builds. Only an op with no equation falls back
to unfolding the dispatcher. For a hand-written step, use
`simp only [cil_step, facts]`.

Each `.memory` operation has one equation per operand shape in
`CIL.Safety.MemorySteps`. It rewrites a step to the operation's own body, such as
`formValue`, `loadValue`, `storeValue` or `add`, so state facts at that level
rather than passing `staticInstruction` or `memoryInstruction` to unfold. Only
the static-field operations still go through `staticInstruction`. A fact stated
at the `memoryInstruction` or `staticInstruction` level is still accepted, through
a slower fallback that runs only when such a fact is supplied; a failed step
reports the per-shape goal. That fallback is part of `cil_checked_step`,
`cil_checked_steps` and `cil_contract_steps` (and the loop tactics built on them)
only: a hand-written memory step, or `cil_checked_step_equations`, with such a fact
must `rw [CIL.Safety.step_memory_eq]` first, and for a `memoryInstruction` fact
also unfold `CIL.Safety.staticInstruction`, or restate the fact at the
`formValue`, `loadValue`, `storeValue` or `add` level. The memory step simp set of those
tactics rewrites `referenceAt` on `.null` and `.address r`, so pointer
arithmetic on a known reference needs no extra fact, and a `referenceAt r = .ok a`
fact about a symbolic `ManagedReference` applies; through `cil_checked_step_equations`
an `add`, `spanItem`, `copyBlock` or `initBlock` step needs
`CIL.Safety.referenceAt_address` passed as a fact. A `.feature f` step pushes `body.profile.evaluate f`. For a known feature,
`cil_step` reduces that expression to the profile field; a symbolic `f` stays
`body.profile.evaluate f`, so a fact about it applies as stated. `cil_step` unfolds a method definition or
literal only as far as its profile, so a fact such as `profile.avx2 = true`
decides the test. Inside `cil_checked_step`, `cil_checked_steps`,
`cil_contract_steps` and the loop tactics, a local fact, proof term or global
theorem stated through `evaluate` or a method's profile projection, including one
quantified over every feature, is normalized to that form. Elsewhere, including
`simp only [cil_step, facts]` and `cil_checked_step_equations`, state the fact on
the field or first run
`simp only [CIL.Safety.reduceMethodProfile, cil_feature] at h`.

### Consumer stepping regressions

The consumer failures reported in #252 are covered by the following proofs. These
use the public tactics with symbolic values and memory; they do not replace the
checked interpreter with consumer-specific execution rules.

| Case | Regression |
| --- | --- |
| Supplied store/load facts take priority over generic equations | `Tests.Automation.step_facts_first`, `applied_step_facts_first` |
| Zero, nonzero and literal branch conditions | `Tests.Automation.branch_from_zero`, `branch_from_nonzero`, `literal_branch` |
| Memory operations use their own equations | `Tests.Automation.asRef_fact_stack`, `load128_fact_stack`, `add_fact_stack` |
| Profile facts decide instruction lookup | `Tests.Automation.feature_op_checked`, `Tests.MethodContract.feature_op_contract_steps` |
| Intrinsic evaluation facts normalize the next stack | `Tests.Automation.evaluated_then_stored`, `evaluated_by_applied_hypothesis` |
| Signed, unsigned and loaded-limb comparisons | `Tests.MethodContract.loaded_signed_branch`, `loaded_unsigned_branch`, `loaded_limb_branch` |
| Signed/unsigned widening and both argument orders | `Tests.MethodContract.ordered_widening` |

Each comparison proof has a 2,000-heartbeat budget. The widening proof handles all
eight combinations of signed conversion, scalar position and reversed arguments
in 12,000 heartbeats, using one `cil_contract_steps 3` invocation per case. Its
arbitrary continuation preserves the actual widened stack and memory, rather than
merely checking that some execution exists. These budgets detect elaboration
regressions independently of machine speed; they are not wall-clock benchmarks.
`ordered_widening_returns` composes that prefix with a concrete suffix which
discards both operands and returns zero, proving that the continuation premise is
satisfiable for every case. The widened value is checked by the prefix theorem.

Every stepping, call and loop tactic closes lookups with `cil_lookup [facts]`:
by evaluation of an `@[cil_code]` extraction, by `rfl`, from a lookup
hypothesis such as `found : program[index]? = some (body profile)`, or by
rewriting feature tests in a profile-dependent body with the facts. A proof
stated over an abstract `program` therefore steps exactly like one over
`Extracted.program`. `cil_checked_steps`, `cil_contract_steps` and
`cil_raise_steps` fail when they cannot take a first step, instead of returning
the goal unchanged.

A segment theorem over an abstract body states where its code sits with
`CodeAt body start segment` ([CodeAt](../CIL/Safety/CodeAt.lean)) instead of
`body.code = leading ++ segment ++ tail` and `leading.length = start`.
Pass `placed` directly to `cil_checked_steps [found, placed]`: `cil_lookup` uses
the placement to fetch literal offsets, including both `start + 1 + 1` and `start + 2`.
It also finds local placement hypotheses without listing them and accepts supplied
placement expressions such as `region.append_left`. The fetched instruction must be
inside the segment and agree with its code. `append`, `middle`, `take` and `drop` move a placement
between a region and its segments, and `rfl` closes a concrete one.
[Tests/CodeAt](../Tests/CodeAt.lean) steps a segment this way.
`Segment program method start finish pre post` packages a checked prefix as a composable
contract. Assertions take the unchanged arguments and a `SegmentState` containing the frame,
stack and memory. Each admitted input supplies an output state and a cost, with an exact
`run (fuel + cost) = run fuel` equation for every continuation fuel. `Segment.trans` composes
adjacent contracts and adds their costs; `Segment.run_exists` applies a successful continuation.
`Segment.consequence` changes assertions by proved
implications. `SegmentState.exact` describes a known state. For these exact-state contracts,
`cil_segment 3 [found, placed, facts]` proves the boundary using `cil_checked_steps` and fails
unless the complete equation closes. `cil_segment_steps [facts]` proves a `SegmentRun`
boundary directly. Neither tactic invents a memory or availability premise.

For numeric-local framing, record successful write equations in `SegmentLocalEffects`.
The destinations must occur in `segmentStores code`, read from the placed instructions.
`Segment.frameLocals` combines these effects with the initial `LocalSnapshots` and
`WritableHomes` to derive snapshots for `untouchedLocals code known`. Effects compose through
`append` or `trans`; one frame-rule application replaces separate disjoint-read proofs for
all retained locals. The numeric slot identities must remain fixed, and the frame-rule placement must belong to
the running method and end at the contract boundary. Indirect writes and
calls need a proved memory effect; absence of a direct `setLocal` is not evidence that an
aliased byte-backed local keeps its value. [Tests/Segment](../Tests/Segment.lean) composes the
UInt256 Add Vector128 reference prefix and Multiply AVX2 vector-input stages with these rules.

For steps depending on hypotheses, use `cil_checked_steps [facts]` with the
relevant proved facts. Branches always use equations before reflexivity, so a fact
can decide the next program counter before the next lookup. A branch condition is
decided from `v = 0` or `Not (v = 0)` on the condition value, or from a literal
condition, so no `CIL.truth` restatement is needed.
Both straight-line and loop-exit automation try return proofs only for fetched
`.ret` instructions, including narrow returns, so other opcodes do not incur
failed return-step simplification.

For loops, import [LoopAutomation](../CIL/Safety/LoopAutomation.lean).
`cil_loop_steps [facts]` composes an execution segment and `cil_loop_finish [facts]`
proves an exit path and its postcondition. Supply an invariant and decreasing
measure to the loop termination theorem; these tactics do not infer termination.
See the [countdown proof](../Examples/Proofs/Countdown.lean).

A loop body that calls a helper composes through the helper's `MethodContract`
([LoopContract](../CIL/Safety/LoopContract.lean)). `LoopSegment` fixes one cost for
every continuation budget, which a contract's existential fuel cannot supply, so
`loop_terminates_induction` asks each iteration for `LoopTerminates` at its own
state while assuming it at every invariant state of smaller measure. Step to the
call with `cil_loop_advance [facts]`, apply the contract with
`cil_loop_call holds input at site [facts]` (`loop_terminates_call`, or
`loop_terminates_call_formed` for `WellFormed` and the static world), re-establish
the invariant from `Returns` and `Confined` in the continuation, reach the next
head with `cil_loop_steps`, and close with `loop_reaches_terminates` and the
assumption. The [counted-loop proof](../Examples/Proofs/CountCalls.lean) never
unfolds the helper or names its fuel; the loop suite reuses it unedited for a
reimplemented helper and requires it to reject a discarded helper result and a
broken count. On the correct build, a nondecreasing measure and an invariant that
holds at entry and exit but is not preserved each fail at exactly that obligation.

A loop whose helper has an `OutcomeContract` composes both of its outcomes
([LoopOutcome](../CIL/Safety/LoopOutcome.lean)). `LoopOutcome post raises state`
is `LoopTerminates post state` when `raises` is `none` (`loop_outcome_none`) and
`RunRaises` of exactly that exception otherwise (`loop_outcome_some`), so the
proof fixes which outcome the loop reaches before stepping it, typically as a
function of the inputs that the invariant ties to each head state.
`loop_outcome_induction` mirrors `loop_terminates_induction`: only a continuing
iteration needs an invariant state of smaller measure. Step with
`cil_loop_outcome_advance [facts]` and continue past a callee whose contract
returns with `cil_loop_outcome_call holds input at site [facts]`
(`loop_outcome_call`, or `loop_outcome_call_formed`), which leaves the
precondition, the `raises` equation and the continuation in either outcome.
Once `raises` is rewritten to the callee's exception, exit with
`cil_loop_outcome_raise holds input at site [facts]` (`loop_outcome_call_raises`);
that exit has no invariant or measure obligation. `loop_outcome_throw` exits at
the loop's own `throw`, and `loop_outcome_next` and `loop_reaches_outcome`
compose paths in either outcome. `ensures_outcome_of_loop` lifts the head outcome
through frame setup to `EnsuresOutcome pre post raises`, which names the outcome
of every permitted input; with `raises` constantly `none` it is `Ensures`
(`ensures_outcome_none`). `loop_outcome_some_refuted` refutes an expected
exception from any settled run that does not throw it.

The [outcome loop proof](../Examples/Proofs/CountUntil.lean) propagates its
helper's exception after earlier successful calls. The loop suite reuses it
unedited for a reimplemented helper and rejects a helper that raises another
type; on the correct build, a nondecreasing measure, a non-inductive invariant
and a wrong specified exception each fail at that obligation.
`Tests/LoopOutcome.lean` derives the normal-only rules as the `none` instances
and proves that unsupported execution, invalid state and fuel exhaustion never
satisfy an expected loop exception.

## Compose calls through contracts

A caller proof that steps into its callee breaks whenever the callee is
reimplemented. State the callee's interface as a `MethodContract` instead
(`CIL.Safety.MethodContract`) and prove the caller against it:

```lean
def addContract : MethodContract AddInput where
  args input := [.reference (.address input.a), .reference (.address input.b), .reference (.address input.res)]
  pre input m := read m input.a 8 1 = .ok (numberBytes input.x.toNat 8) ∧
    read m input.b 8 1 = .ok (numberBytes input.y.toNat 8) ∧ access m input.res 8 1 true = .ok ()
  footprint input := [(input.res, 8)]
  post input _ final values := values = [] ∧ read final input.res 8 1 = .ok (numberBytes (input.x + input.y).toNat 8)

theorem root_holds (add : addContract.Holds Extracted.program addTo) : rootContract.Holds Extracted.program root
```

`pre` holds formation, authority and the permitted aliasing; the example lets
`res` overlap either input. `Holds` is `Ensures` with the footprint added to the
postcondition (`Holds.ensures`), and fuel stays existential so callers never
depend on a callee's step count. `Confined footprint before after` is the memory
guarantee: earlier allocations and write authority are unchanged, and bytes and
read authority change only inside the footprint (a write grants read access to
what it wrote). `Confined.trans`, `Confined.widen`, `Confined.write`, `Confined.read_eq`
and `Confined.access_write` compose and consume it. A callee with locals writes its own
frame too: list those slots in the footprint while executing, then drop them with
`Confined.forget_fresh` and cover frame entry and teardown with `Confined.then_below`.
`Outside.nil` and `Outside.cons` are simp rules, so `simpa using ⟨hr, hq⟩` closes a
word footprint from per-word `OutsideWord` facts; `Outside.word` builds it as a term.
`Within inner outer` states that an interval lies inside another of the same allocation:
`Confined.widen_within` widens a footprint to one whose entries enclose it, and
`Confined.write_within` confines a write that lies inside one entry, so four limb writes
satisfy a contract that declares one 32-byte output. Entries may overlap.
`Apart r width entry` states that two intervals share no byte, in different allocations
or at disjoint offsets of one. `Confined.read_apart` keeps a checked read of older memory
apart from every entry, taking the allocation's age from `WellFormed`;
`Confined.cells_apart` keeps every byte of an allocation no entry names, and
`WordSnapshots.after_confined` (`CIL.Safety.ConfinedSnapshots`) keeps remembered words.
`LocalSnapshots` (`CIL.Safety.LocalSnapshots`) remembers locals of every numeric kind, such
as vectors and int32s; `LocalSnapshots.after_confined` keeps them across such a call, and
`after_write_apart`, `after_below` and `store` across writes, frame changes and local stores.
`snapshots.load value specified` is a step fact for `.local`, so stepping tactics take it.

Import `CIL.Safety.LocalSnapshotSteps` to step through numeric local stores and reloads with
`cil_checked_steps (snapshots := snapshots) [facts]`. Use it on a checked `run` equality or
an existential result such as `∃ after, run ... = .ok (after, result)`. The local context must
justify `WritableHomes`, memory well-formedness, each home lookup and write access. The tactic
introduces each store's new memory, updated snapshots and preserved access facts, so later
stores need no manually split execution segments. Loads use the latest remembered value;
overwrites replace it. It stops at an unsupported step or an unproved obligation, and fails
if it takes no step. It does not infer authority, initialization, or preservation across calls
and unrelated writes. Ordinary `cil_checked_steps [facts]` is unchanged.
[Tests/LocalSnapshotSteps](../Tests/LocalSnapshotSteps.lean) contains complete vector/int32
store-and-reload examples and rejection tests.

A snapshot overlapping the footprint needs a postcondition instead. The contract fixes no profile:
the program does. `MethodContract.Holds.reprofile` (`CIL.Safety.ProfileContract`, with
`OutcomeContract` and `HoldsCLR` forms, and `_statics` forms of the first two for a contract
indexed by `programStaticDescriptors`) carries a contract proved for a program whose methods
all use profile `p` to `CIL.reprofile program q` for any `q` that agrees with `p` on the
program. `CIL.Program.ProfileAgreement.of_flags` reduces agreement to the flags in
`program.profileReads`, which `decide` checks for concrete profiles, so one proof covers every
profile in a family. A separate per-profile extraction is covered once it is shown equal to
the reprofiled program, by `rfl` when only the profiles differ.

`leancil export-contracts` accepts one manifest entry for such a family:

```json
{
  "method": "Library::Supported()",
  "contract": "Public.supported",
  "theorem": "Proof.family",
  "program": "Reference.program",
  "referenceProfile": "x64-sse2",
  "profiles": [
    { "profile": "x64-sse2", "artifact": "extractions/sse2" },
    { "profile": "x64-sse42", "artifact": "extractions/sse42" },
    { "profile": "x64-v3", "artifact": "extractions/v3" }
  ]
}
```

The surrounding manifest still provides `schema`, `assembly`, `proofRoot` and `interface`.
Each artifact's `verification.json` selects the shared proof source under `proofRoot`.
The family theorem has shape
`∀ q : FeatureProfile, Predicate q → contract.Holds (reprofile Reference.program q) 0`,
where the concrete predicate is decidable. Both method and outcome contracts are supported.
The selected artifacts must include `referenceProfile`. Its extraction is checked against the
same DLL, copied into a reserved generated module, and compiled separately from author macros.
Its compiled artifacts are frozen before author code runs and checked again afterward.
Every profile must prove by `rfl` that the named reference program equals this fixed program;
a definition that changes with the current extraction cannot substitute a different body.
The reference program must use `referenceProfile` uniformly. Each profile receives its own
ordinary extraction check, layout check, theorem audit and kernel replay; generated proofs
instantiate the predicate with `by decide +kernel` and establish the exact program equality
with `rfl`. Because the family theorem already concludes a reprofiled program, no second
transport or handwritten per-profile proof file is needed.

This manifest form covers same-flag transport: a separate checked `ProfileAgreement.of_flags`
obligation rejects any selected profile that disagrees on a reference program read flag,
including intrinsic prerequisites, and reports the flag's name. It deliberately does not
accept general families whose observed branches differ. Use profile templates for those
proofs. Even an otherwise valid family is rejected when extraction pruning, method numbering,
instructions or metadata make its program differ from the reprofiled reference. The exact
equality and agreement statements are independently audited, so proof-source macros cannot
replace these checks. Nothing is published unless all selected profiles pass.
Published source bundles retain every selected extraction; full verification freshly extracts
both the selected profile and its fixed reference from the pinned implementation DLL, then
repeats the family checks before composing the caller theorem.

Profiles must be distinct built-in names and match their artifacts. A family entry cannot
also specify `artifact`; ordinary single-profile entries are unchanged. Family transport
currently requires a closed extraction without imported-contract slots. Explicit type-initialization
premises remain bound to each exported profile; static-value assumptions remain unsupported.
Full source-bundle verification rejects initialization premises, as for single-profile exports.

For a program with no profile reads, use the same `ProfileAgreement.of_flags` rule:
an equality `empty : program.profileReads = []` discharges its premise with
`by simp [empty]`. This replaces `profileIndependentCheck` and
`profile_independent_agreement`; no separate profile-independent checker is needed.

A contract may also type its result: `MethodContract Input Output` adds
`results : Output → List Value`, and `post` speaks of the `Output`. `Returns`
requires the returned values to equal `results out` for some `out` satisfying
`post`. Without `Output`, `results` is the identity and `post` sees the values:

```lean
def mixContract : MethodContract (CIL.W64 × CIL.W64) CIL.W64 where
  args input := [.scalar (.i64 input.1), .scalar (.i64 input.2)]
  results v := [.scalar (.i64 v)]
  pre _ _ := True
  footprint _ := []
  post input _ _ v := v = input.1 * 3 + input.2
```

In the caller, `cil_contract_steps [facts]` steps an existential-fuel goal through
ordinary instructions and calls with supplied evidence. Mark a proved `MethodContract.Holds`
theorem `@[cil_contract]`, or include its proof in `facts`, to apply it at a matching callee.
The theorem's program and method binding must match the actual call; required binding
premises are checked. Input fields are inferred from the encoded arguments. The precondition
is proved from facts when possible, otherwise it remains a goal before the continuation.
The continuation receives the result, footprint and postcondition. Contracts merely present
in the local context are not automatically selected.

A supplied successful child invocation, with fixed or existential fuel, or an
`InvocationCertificate`, also composes without unfolding the helper body. Fixed-fuel
`cil_checked_steps` can reuse a matching invocation or certificate at its actual child
budget; a proof at a larger budget does not justify a smaller one. Contract and
existential-child composition use `cil_contract_steps`, whose fuel remains existential.

Without matching evidence, the contract stepper stops at the call.
`cil_contract_call holds input at site [facts]` explicitly applies
the contract at a `bind_call` site (or the fetched call without `at`), leaving the precondition and then a continuation over the
callee's final memory, values, invocation, frame and `Returns`. Destructure
`Returns` as `⟨out, rfl, post⟩` and unfold the contract (`dsimp only [mixContract]`)
so the stack holds the encoded output.
Use `cil_contract_steps n [facts]` to take at most `n` instruction steps and
leave the remaining goal for a continuation. With `n = 0`, no instruction is
executed. `cil_contract_steps [facts] until continuation` tries the continuation
before each step, including at the initial goal. It stops when the continuation
closes the goal or no instruction can be stepped.
`cil_formed_call` (`run_call_of_contract_formed`) also takes the caller memory's
`WellFormed` and hands the continuation the callee's `final.WellFormed` and
static-world preservation, so contracts need not restate either; `cil_formed_outcome_call`
does the same for `cil_outcome_call`.

`StaticWorldPreserved program before after` names static-world preservation.
Use `left.trans right` to compose it across calls. `FrameInvariants program before after`
bundles `after.WellFormed` with that preservation. Its `formed` and `staticWorld`
projections give each fact, and `left.trans right` composes both invariants.
`call_frame_invariants` and `construct_frame_invariants` return this bundle.
Both names are abbreviations, so existing conjunction proofs and formed-call
continuations keep their proof structure and argument order.

Store facts may name their values in source form, such as
`write m r (numberBytes (a + b + c).toNat 8) 1 = .ok m'`. Each checked step
simplifies the goal with the default simp set, its interpreter definitions and
the facts. Fact preparation also adds each local fact normalised by the default simp set and
the supplied non-local facts, so both sides meet in the same form. Supply any
definition the computed value is stated through, such as a carry or borrow
word, among the facts. The original hypotheses stay in the proof context and in
the simp set; a fact that still differs stops the steps at its instruction, with
the hypothesis shown as stated. Hand-written stepping can use the same
simplification, with an optional simp configuration, as
`cil_fact_simp (config := ...) [definitions] [facts]`.
`cil_checked_steps`, `cil_contract_steps`, and `cil_raise_steps` prepare local
facts once at entry. All later steps reuse these copies, including nested
checked calls. The original hypotheses stay in the local context.

When a local fact starts with `∀ index : Fin n`, preparation instantiates every
index for a concrete `n` up to 64. Larger or symbolic domains keep their original
quantified fact without eager enumeration. Any later binders, such as a stack suffix `rest`, stay
quantified. This lets one four-limb field-load fact rewrite offsets 0, 8, 16,
and 24. Preparation and stepping also normalize Fin constructor indices and
the projection of the literal `3`. For example, a fact `words 1 = 0` applies to
a value read as `words ⟨1, proof⟩`.

Enable `trace.CIL.factNormalize` to see one event per supplied local proposition
when it is prepared. `Tests/StoreFacts.lean` counts exactly 12 such events for a
27-instruction run. This count checks normalization frequency; it is not an
elapsed-time measurement.

[`Tests/StoreFacts.lean`](../Tests/StoreFacts.lean) checks carry and borrow
stores and rejects a wrong value, address or memory state.

`Tests/MethodContract.lean` proves a caller from two contracts without unfolding
either callee. `Tests/MethodContract.cs` verifies that caller proof unedited
against a build whose helpers are reimplemented and renumbered, and refutes
each contract with a concrete run on builds with an arithmetic or an aliasing
bug; `invoke_ok_unique` ties a computed run to the contract's existential one,
and `invoke_ok_observation_unique` does so for one observation of it, such as
the returned values, so the refutation never compares memories.

A contract whose precondition implies well-formed memory and a valid static
world can also keep the `InvocationCertificate` of each call:
`MethodContract.Holds.certified` turns `Holds` into `MethodContract.Certified`,
whose clause adds the certificate with its visited-state and returned-state
invariants; `Certified.holds` recovers `Holds`, and `Certified.weaken` keeps
the certificate through a `Refines`. `InvocationCertificate.of_invoke`
certifies any successful `invoke` from those two premises, and
`InvocationCertificate.of_run` certifies a run of the frame that checked
arguments enter. At a call site, `run_call_of_certified` (from a `Certified`
callee) and `run_call_of_contract_certified` (from `Holds`, a well-formed caller
memory and a valid static world) hand the continuation the callee's certificate,
which `run_call_of_contract` drops. At a fetched call, `cil_certified_call
certified input [facts]` leaves the precondition and then the continuation, and
`cil_contract_certified_call holds input [facts]` leaves the precondition, the
caller memory's `WellFormed`, its static world and then the continuation. Both
accept `at site` like `cil_contract_call`.
`Tests/InvocationCertificates.lean` uses each of them.

`ValidCall memory inputs outputs` states that memory is well formed, every input
buffer is readable and every output buffer writable. `CIL.Safety.CallingTransport`
carries it to later memory so a caller can pass the same buffers again:
`ValidCall.after_write` after any checked write, `after_enterFrame` after frame
entry, `after_below` across memory that keeps old allocations' access
(`AccessBelow`, or `MemoryBelow.accessBelow`), and `after_confined` across a call
whose footprint the inputs lie `Apart` from. `mono` drops buffers, and
`input_bound` / `output_bound` give the identity bound those relations take.

## Describe buffer contents

`CIL.Safety.BufferContents` states what a contiguous run of integer elements
holds, over the checked memory model. `Contents m base width xs` says element `i`
of `xs : List (BitVec (8 * width))` reads back at `base.element width i` (offset
`base.offset + width * i`, same allocation) as `numberBytes x.toNat width`, with
the byte alignment scalar loads and stores use. `Contents.load` (from
`load_scalar_of_read`) turns an element at any `ScalarWidth` (1, 2, 4, 8, 16, 32
or 64 bytes) into the `loadValue` result `numericOfWidth width x.toNat`: widths 1
to 4 zero-extend to `.i32`, 16 and up are vectors, and width 8 yields
`.i64 (BitVec.ofNat 64 x.toNat)`, so `Contents.load_word` (`load_word64_of_read`)
stays the direct route to `.i64 x`. `byteNumber_elementBytes` decodes a whole
buffer as the sum of its elements, element `i` scaled by `256 ^ (width * i)`, and
`byteNumber_elementBytes_lt` bounds it by `256 ^ (width * xs.length)`. Rewriting
with it at a literal width such as 8 makes the kernel unfold the powers and can
hit deep recursion; prove the sum at symbolic width and instantiate, as
`byteNumber_elementBytes_four` does for four limbs (instantiate, then
`simp only [Nat.reduceMul, Nat.reducePow] at h`), or peel one limb at a time with
`byteNumber_elementBytes_cons`. Contents grant no write authority:
`Writable m base width start count` is write authority alone, and
`Filled m base width xs room` is an initialized prefix followed by `room`
writable elements that need not be readable. An empty `Contents` asserts
nothing. `Contents.read` joins the elements into one checked read only given that
read's `access`, so a zero-width read keeps its formation check and elements
separated by a reference slot do not join; `Contents.of_read` splits a checked
read through `read_slice_bytes`. `take`, `drop` and `append` move between
adjacent subranges. `Contents.write_element` and `Contents.write_run` update one
element or a run; `Contents.after_write_apart` and `Contents.after_confined` keep
contents `Apart` from a write or every footprint entry, including disjoint slices
of one allocation; `Filled.push` extends the prefix by one element write without
reading the room. `Filled.fill` and `Contents.transform` prove fill and in-place
map loops of any length (`writeElements`, `transformElements`) as sequence
properties confined to the buffer; `add_element` steps `Unsafe.Add` to an element, and the
[buffer fill proof](../Examples/Proofs/FillWords.lean) carries `Filled` as the invariant
of a compiled loop. `Tests/BufferContents.lean` checks unchanged
neighbouring bytes and sibling slices, and refutes uninitialized, past-end,
overlapping, unjoined and stale claims.

## Construct structs through contracts

A `newobj` of a reference-free struct allocates caller-owned storage, writes
zero to every byte, then runs the constructor with that storage as `this`. The
constructor's interface is an ordinary `MethodContract` whose first argument is
`this`; `MethodContract.Constructs c size this value` adds that it returns no
values and that `post` reads back all `size` bytes at `this` as `value`:

```lean
def pairContract : MethodContract PairInput Unit where
  args input := [.reference (.address input.this), .scalar (.i64 input.low), .scalar (.i64 input.high)]
  results _ := []
  pre input m := m.WellFormed ∧ access m input.this 16 1 true = .ok ()
  footprint input := [(input.this, 16)]
  post input _ final _ := read final input.this 16 1 = .ok (pairBytes input)

theorem pair_constructs : pairContract.Constructs 16 PairInput.this fun input _ => pairBytes input :=
  ⟨fun _ => rfl, fun _ _ _ _ readback => readback⟩
```

The storage does not exist before the step, so a caller names the contract
input as a function of it. `cil_contract_construct holds constructs input [facts]`
applies `run_newAggregate_of_contract` at the fetched `newobj` and leaves the
caller memory's `WellFormed`, the precondition over the fresh storage, and a
continuation that resumes at `pc + 1` with the read-back value on the stack.
Both obligations receive `ConstructStorage memory updated this size`: the
storage reads back as `size` zero bytes, is writable at full width, is
allocated at `memory.nextIdentity`, and the step kept all older memory. The
continuation also gets the constructor's invocation, the final memory's
`WellFormed`, static-world preservation, `Confined` and `post`. No invocation,
step or `loadLocal` equation is stated. `ConstructStorage.confined` moves
`Confined` back to the memory before `newobj`; `Confined.forget_fresh` then
drops the storage, which the caller's frame owns and expires on return.

Because `newobj` zeroes the storage, a constructor that leaves a field
unassigned still has a full-width readback: the field reads back as zero, not
as an uninitialized read. A contract may take that zero readback as a
precondition. `run_construct_of_contract` and `run_construct_of_contract_formed`
take the construct step equation instead, like `run_call_of_contract`; they
cover aggregate storage only. `read_append` joins adjacent field reads into the
full readback, and `Confined.write_within` confines a field write to the
whole struct.

`Tests/ConstructContract.lean` proves a caller that constructs a 16-byte and a
32-byte (four-limb, `UInt256`-shaped) struct and reads a field of each, from
the constructors' contracts alone; a constructor that assigns one of two fields;
and rejections: a contract without write authority over its storage, a
constructor that writes outside its footprint, and an 8-byte readback at a
16-byte site. `Tests/ConstructContract.cs` verifies that caller proof unedited
against a build whose constructors write their fields in the opposite order,
and refutes the constructor's contract on a build that stores a wrong field.

## Name exceptional outcomes

An `OutcomeContract` (`CIL.Safety.OutcomeContract`) adds
`raises : Input → Memory → Option String` to a `MethodContract`: where it is
`some exception` the method must end in exactly `.thrown exception` (`Raises`),
and elsewhere the normal clause applies. Fuel exhaustion, unsupported
instructions and memory faults never satisfy `Raises`, so a contract cannot
be met by getting stuck. Memory after a throw is not observable to the caller,
so `Raises` states none; runtime exceptions count only where the semantics
models them as `.thrown`.

```lean
def percentContract : OutcomeContract CIL.W64 CIL.W64 where
  args v := [.scalar (.i64 v)]
  results out := [.scalar (.i64 out)]
  pre _ _ := True
  footprint _ := []
  post v _ _ out := out = v
  raises v _ := if v ≤ 100 then none else some "System.ArgumentOutOfRangeException"
```

`cil_raise_steps [facts]` steps a `Raises` goal to its `.throw`;
`cil_outcome_call holds input at site [facts]` continues after a call the
callee's contract says returns, whether the caller then returns or raises, and
`cil_outcome_raise holds input at site [facts]` closes a `Raises` goal by
propagating the exception the callee's contract names.
`MethodContract.Holds.outcomes` lifts a normal-only contract, and
`invoke_unique` ties a computed fault to the contract's existential one.

`Tests/OutcomeContract.lean` proves every outcome of a two-level chain from the
callees' contracts: `Strict` propagates `Percent`'s exception, returns, or raises
its own after `Percent` returns, and `Root` reads all three off `Strict`'s contract. `Tests/OutcomeContract.cs` verifies those proofs against the compiled
build, and refutes the callee's contract with concrete runs on builds with an
off-by-one threshold or a different exception type.

Import `CIL.Safety.RuntimeExceptions` to name modeled arithmetic failures with
`RaisesCLR` and `OutcomeContract.HoldsCLR`. This contract mode uses the existing
arguments, preconditions, normal-return clause, footprint and `raises` field.
Its fixed `ExecutionFault.clrException` mapping is:

| Fault | Named CLR exception |
| --- | --- |
| `.thrown exception` | `exception` |
| `.arithmetic .overflow` | `System.OverflowException` |
| `.arithmetic .divideByZero` | `System.DivideByZeroException` |
| Every other fault | None |

Checked add, subtract, multiply and integer conversions report overflow through
this mapping. Integer division and remainder by zero report divide-by-zero.
The admitted runtime model reports overflow for signed minimum divided by
negative one, including its remainder instruction. Invalid arithmetic operands,
invalid bounds, memory faults, unsupported instructions, invalid state and fuel
exhaustion have no name in this mode. `Raises` and `.thrown` keep their existing
meaning. `OutcomeContract.Holds.clr` lifts an existing thrown-outcome proof.

For a UInt256 `Divide` or `Mod` contract, select
`some "System.DivideByZeroException"` in `raises` when its divisor is zero and
prove `HoldsCLR`. Both an explicit throw and the mapped arithmetic failure can
establish this exact outcome. The proof must still reach that fault through the
actual extracted program. `run_fault_raisesCLR`, `run_next_raisesCLR` and
`raisesCLR_of_run` compose that execution; `run_call_raisesCLR_of_contract`
propagates a callee contract's named outcome. `RaisesCLR.not_of_invoke` refutes a
wrong name from a settled checked invocation.

`Tests/RuntimeExceptions.lean` proves all mapped cases and refutes wrong names.
It also proves unsigned division and remainder by zero for every dividend and
caller memory. `Tests/RuntimeExceptions.cs`, run by the outcomes suite, checks
the CLR type and verifies each positive contract and wrong-name refutation
against its compiled C# method.

## Derive public contracts

A method's proved contract can be more detailed than its callers need. Export a
smaller interface by proving that the internal contract refines it, without
unfolding or executing the method again:

```lean
theorem add_public : addPublic.Holds Extracted.program addTo := add_internal.weaken add_public_refines
```

`MethodContract.Refines internal exported` requires the same `args` and `results`
encodings, the exported precondition to imply the internal one, every internal
footprint entry to lie `Within` an exported entry under the exported precondition
(so `Confined.widen_within` applies), and the internal postcondition to imply the
exported one under the exported precondition and the internal footprint's
`Confined`. That last premise lets the exported post state a frame fact, such as a
read apart from the footprint surviving through `Confined.read_apart`.
`MethodContract.Holds.weaken` turns a proved `Holds` and a `Refines` into the
exported `Holds`.

`OutcomeContract.Refines` adds that both contracts select the same outcome (`raises`)
under the exported precondition; the footprint and postcondition premises apply
only where that outcome is normal return. `OutcomeContract.Holds.weaken` derives
the exported outcome contract, and `OutcomeContract.Refines.of_method` builds a
refinement from a normal one and the agreeing outcomes. A stronger precondition
can exclude every exception, after which `OutcomeContract.Holds.normal` yields a
normal-only contract. Both `Refines` are reflexive and transitive.

`Tests/ContractConsequence.lean` derives a bounded `Percent` contract and a
framed `AddTo` contract over an enclosing region, and proves callers through the
derived contracts at their call sites, in both returning and raising outcomes.
Its rejections are proved negations: an unjustified stronger postcondition, a
weaker precondition, a smaller footprint and a changed exception type each
refute the `Refines` premise and the derived `Holds` on a concrete input.

## Inherit a callee's contract in a forwarder

Overload forwarders and instance-to-static wrappers compile to
`ldarg*; call k; ret`. `MethodContract.Holds.forward` (`CIL.Safety.Forwarders`)
gives such a method its callee's contract with the forwarder's own argument
encoding, `contract.withArgs forwarded`, without stepping either body:

```lean
theorem sum_forwards : sumContract.Holds Extracted.program sum :=
  add_public.forward (loads := plainLoads [0, 1, 2]) (narrow := none) sum.found addTo.found
    ⟨rfl, rfl, rfl, rfl, rfl, rfl⟩ (fun _ => rfl) (fun _ _ _ => plainLoads_unchanged _ _)
    (fun _ _ _ _ member => .inl member)
    (fun _ _ _ => rfl) (fun _ _ _ _ _ => trivial)
```

`Forwards body calleeBody loads callee narrow` fixes the body to
`forwarderCode loads callee narrow` with no locals, vector argument homes or
parameter homes, so frame entry and exit leave memory unchanged and the callee's
precondition, footprint and postcondition carry over verbatim. The loads are data:
each is an argument index and the narrowing the extractor attaches to `bool`,
`byte`, `sbyte`, `short` and `ushort` parameters (`plainLoads` for wider ones).
The callee's arguments must be the forwarder's at those indices, each kept by its
load's narrowing (`LoadsUnchanged`); every forwarder argument must reach the
callee or be valid under the precondition, since the forwarder's own invocation
checks them all; the call must expose no unspecified vector bits; and a narrowed
`ret (some kind)` must not change the callee's result (`ReturnsUnchanged`), which
holds for a boolean. Use `Holds.weaken` afterwards to export a different contract.

`MethodContract.Holds.forward_out` covers `ldarg*; ldloca 0; call k; ret`, which
passes the address of a fresh numeric local (not a reference, span or array, which have
no byte home) as a last out argument and drops it. `ForwardsOut.notArray` excludes every
array element kind; `make_fitting_local` requires the same premise after `notSpan`.
The local may hold any initializer that fits its kind; the extractor emits
`.unmodeled` without `InitLocals` and the kind's zero with it. The callee runs in
the memory after frame entry and the result is read after the local expires, so
the forwarder's contract `outer` is related to the callee's `inner` through
`extend input home` and premises over those memories. The callee's arguments must
be the forwarder's selected by the loads followed by the home, each kept by its
load's narrowing and none with unspecified vector bits; `outer.pre` must give a
well-formed memory in which every forwarder argument is valid (`checked`), since
the forwarder checks them all; `inner.pre` must follow from `outer.pre` with the
home fresh, writable and holding its initializer (`LocalHolds`); the `inner`
footprint must name fresh storage or lie inside `outer.footprint`; the two
contracts must encode results alike, as scalars that survive the local's expiry
and that a narrowed `ret` keeps; and `outer.post` must follow from `inner.post`
once the frame has expired. The footprint is checked by the lemma
(`Confined.across_frame`). The home's alignment is not surfaced, so a callee whose
precondition requires it cannot be composed yet.

## Compose through imported contracts

A callee from another assembly has no body in the caller's extraction. Give it
an import slot (`CIL.Safety.Imports`): slot `j` is method index
`importIndex base j = base.length + j`, past every extracted method, so running
the caller's program alone faults `invalidState` at the call (`run_call_unlinked`,
`importIndex_unlinked`). Do not put a stub body there: a stub's contract is false,
so a theorem assuming it proves nothing.

Prove the caller over every program that links its own, assuming only the
import's contract:

```lean
def importsAdd (linked : CIL.Program) : Prop := addContract.Holds linked (importIndex Extracted.program 0)

theorem root_given : HoldsGiven Extracted.program importsAdd (fun linked => rootContract.Holds linked root)
```

`Links base linked` means `linked = base ++ rest`, so every extracted method
keeps its index (`Links.refl`, `Links.trans`, `Links.found`). `HoldsGiven base
imports claim` is `∀ linked, Links base linked → imports linked → claim linked`.
Start the proof with `rintro linked ⟨rest, rfl⟩ addHolds`; the step and call
tactics find methods in `Extracted.program ++ rest` unchanged. A helper proved
on the extracted program alone transfers with `MethodContract.Holds.extend` or
`OutcomeContract.Holds.extend`: `run_extend` shows a run that never faults
`invalidState` gives the same result in any linked program, and a raised
exception is not `invalidState`. `HoldsGiven.discharge` instantiates the claim
for a concrete linked program whose import meets its contract, and
`HoldsGiven.closed` states a claim that needs no import.

In an extraction, `bind_import addTo := "System.Void Lib.Adder::AddTo(...)"` resolves
the signature through `Extracted.importSignatures` and defines `addTo` as
`Extracted.program.length + j`, with `addTo.slot`, `addTo.signature` and
`addTo.unlinked` (`Extracted.program[addTo]? = none`) checked by `rfl`; `bind_call`
then names its call site. The certificate accepts a call there only when
`Extracted.imports` has a slot with the site's identity and arity (see
[SOUNDNESS](SOUNDNESS.md)); the extractor does not resolve imports yet, so
`Extracted.imports` and `Extracted.importSignatures` are empty.

`Tests/Imports.lean` proves `Root` against an imported `AddTo` while reusing the
closed `Mix` proof, discharges it for one appended implementation, shows the
unlinked program faults at the import's call so its contract holds only
vacuously, and composes an imported raising `Percent` through both outcomes of
`Strict` and `Root`. The identity checks that bind a slot to a certified library
implementation are not part of this rule; relocating a library into the slot is
described next.

## Read control flow off one step

`CIL.Safety.StepFlow` says where a successful `step` can go without unfolding it.
`step_next_target`: an action that stays in the frame resumes at `pc + 1` of a
continuing instruction or at one of `op.targets`. `step_callee`: only `.call`,
`.newVector256` and `.newAggregate` enter a method, the one they name
(`Op.callees`). `step_call_action` and `step_newVector256_action` /
`step_newAggregate_action` separate a call from a construction. The module
imports only the step simulation, so a consumer reasoning about reachable pcs
does not compile the import and linking layers.

## Move a run that starts inside a region

Embedding relates whole bodies. When only a suffix is shared, `CIL.Safety.RegionRun`
cuts the rest away first. `RegionClosed program region` says fallthroughs, targets
and callee entries of region instructions stay in the region; `regionClosedCheck`
decides it for a region listed as `(method, lower)` suffixes (`inStarts`).
`AgreesOn program other region` says `other` has the same methods and metadata and
the same instruction at every region pc; `AgreesOn.set` and `code_agrees_of_drop`
build it for one replaced body. Then `run_congr_region` gives equal runs from any
region pc, faults included. Masking the code outside the region with `.unsupported`
makes it dead for `Embeds`, so `run_refines` carries the suffix run on to a body
with a different prefix; `Tests/RegionRun.lean` moves a suffix after inline code
to the same suffix after a helper call, one pc earlier.

For a long suffix, import `CIL.Safety.Embedding.Suffix` and use
`CIL.Embedding.BodyRefines.of_relocated_suffix`. It uses one list equality:
`actual.code.drop start = (expected.code.drop lower).map (Op.relabel (fun pc => pc - lower + start))`.
The expected prefix must contain only dead instructions. All branch targets in
the suffix must be at least `lower`. The constructor also requires equal method
metadata, equal static descriptor lists, and equal static lookups at each moved
pc. If `lower = 0`, `start` must also be zero to preserve method entry.

The resulting map, `suffixRename lower start`, sends prefix pcs to zero and
suffix pcs to `pc - lower + start`. Pass the proof to `ProgramRefines.set_body`
and then `run_refines`. This avoids evaluating `sites` and `pick` for each
instruction. `Tests/RegionRun.lean` combines it with `run_congr_region` for a
100-instruction suffix with a symbolic feature profile and callee index. The
test includes conditional, switch, and wrapped native branch targets and uses
the default heartbeat limit.

## Link separately extracted libraries

A library extracted on its own calls its helpers by its own method indices.
`CIL.Safety.Linking` relocates it into a linked program. `Op.relocate f` renames
only the method index of `.call`, `.newVector256` and `.newAggregate`
(`Op.callees`); pcs, locals, profiles and static sites are unchanged.
`Closed lib` says every callee index in `lib` is one of its methods
(`Closed.of_check` decides it), and `RelocatesInto lib linked f` says method `i`
sits at `f i` relocated by `f`. Then `run_relocate` and `invoke_relocate` give
exactly the same result: the same memory and values on return, and on a fault
the same pc and fault with only its method index renamed to `f method`. A raise
is still the same `.thrown`, so `MethodContract.Holds.relocate` and
`OutcomeContract.Holds.relocate` move a contract proved on the library alone to
its relocated index.

A `Library` is its exported entry and its private helpers. `link app libs` puts
library `j`'s entry at import slot `importIndex app j` and all helpers after the
entries, library by library (`linkSlot`). `link_links` and `link_relocates`
hold by construction, so `composed` discharges a caller's `HoldsGiven` for the
concrete linked program from contracts proved on each library alone:

```lean
theorem root_composed : rootContract.Holds (link Extracted.program [addLib]) root :=
  composed (specs := [addContract.relocatable]) (root_given.mono fun _ met => met 0 (by decide)) rfl
    closed proved
```

Here `closed` and `proved` are each library's `Closed` and `Holds` facts.
`Imports app specs` names one `Relocatable` property per slot, so libraries may
export contracts of different types. Each library exports only its index-0
method. Static identities are not renamed: two linked libraries that use the
same identity for different bytes fault `invalidState` at the second static
access, so a collision can only make a proof fail, never prove a false statement.

`Tests/Linking.lean` links an `AddTo` library whose entry calls its own `Sum`
helper (renamed from index 1 to 3) and proves the imported `Root` for the
concrete linked program, then links a `Percent` library whose helper raises and
shows the exception reaches `Root` through two relocated calls.

## Reuse framework contracts

When extending generic safety proofs, reuse the facts established by the shared
dispatch or traversal proof. Names in this table are in `CIL.Safety`, except
the base relabeling helpers in `CIL.Embedding`.

| API | Reusable information | Source |
| --- | --- | --- |
| `RunTrace` | Successful execution through next, return, call and construction cases | [ExecutionTrace](../CIL/Safety/ExecutionTrace.lean) |
| `FrameSetup` | Fresh ownership, frame allocations, preservation below the allocation boundary, static bindings and conditional validity | [FrameSetupLemmas](../CIL/Safety/FrameSetupLemmas.lean) |
| `InstructionContract` | Memory effects and conditional output-value validity from one instruction analysis | [InstructionMemoryLemmas](../CIL/Safety/InstructionMemoryLemmas.lean) |
| `StaticInstructionContract` | Corresponding contract for static-memory instructions | [StaticMemoryLemmas](../CIL/Safety/StaticMemoryLemmas.lean) |
| `StepContract` | Memory/frame effects and conditional live-value validity for a checked action | [ExecutionInvariants](../CIL/Safety/ExecutionInvariants.lean) |
| `Fallthrough`, `Branching` | Shared relabeling proofs for base instruction families | [BaseStep](../CIL/Embedding/BaseStep.lean) |

These contracts retain their hypotheses. For example, `InstructionContract.values`
requires well-formed input memory and valid input values; its memory-effect field
does not require those additional hypotheses. `RunTrace` describes successful
execution; fault-preservation proofs need the appropriate equivalence lemmas.

## Keep proof work local

Prefer a small `change` or an instruction equation over repeatedly unfolding
`run`, `CIL.Safety.step` and `CIL.step`. For generic opcode proofs, split the
opcode and stack shape before splitting operand constructors, and close
definitionally equal cases early. Share the remaining family-level reasoning.
For concrete execution, compose steps first and simplify the resulting value
equation separately when needed.

Measure changes with fresh Lean processes and prebuilt dependencies on both
revisions. Alternate baseline and candidate runs serially on the same machine,
and include downstream consumers. Record elapsed time, CPU time, `.olean` bytes,
peak process memory and kernel replay separately. A smaller artifact can still
require expensive elaboration or cause callers to repeat work; peak memory also
includes imported environments. Keep kernel replay and the axiom audit enabled.

The [validation guide](VALIDATION.md#proof-automation) describes the regression
coverage and commands for checking the proof tactics.

## Bind bodies to the extraction

Reusable execution and contract theorems are stated over a generic program and
bound to each extraction by a method-body equality. Prove those equalities with
`cil_body` (from `CIL.MethodBinding`, also imported by `CIL`) instead of `rfl`:

```lean
import CIL.MethodBinding

have found : Extracted.program[2]? = some (Full.fullBody Extracted.profile 9 5 7) := by cil_body
```

`cil_body` runs `rfl`, so the proof is the same kernel-checked `Eq.refl`. Only
when `rfl` fails does it evaluate both closed sides and report, for each
differing `Method` field, the first differing index, both elements and both
lengths, instead of only `rfl`'s type mismatch:

```text
cil_body: rfl could not prove the method-body binding
method index 1
field code: first difference at index 1 (left length 6, right length 6)
  left:  CIL.Op.brzero 10
  right: CIL.Op.brzero 4
```

The left side is the extraction's body. An index past the end of the program is
reported with the program's length. The diagnostic is computed after the
failure through compiled evaluation and is never proof evidence; it also works
for `Method = Method` goals. `Tests/MethodBinding.lean` covers both outcomes.

### Methods by signature

Extraction numbers methods by the reachable call graph, so adding or reordering
a callee renumbers unrelated methods and breaks every literal index. Name them
by their exact emitted signature (`Extracted.signatures`) instead:

```lean
import CIL.MethodIdentity

bind_method root rootBody := "System.UInt64 Examples.Calls::Root(System.UInt64,System.UInt64)"
bind_callee left leftBody := "System.UInt64 Examples.Calls::Left(System.UInt64,System.UInt64)" from rootBody

theorem left_spec (x y : W64) (m : Memory) :
    invoke Extracted.program 4 left [.i64 x, .i64 y] m = some (m, [.i64 (x - y)]) := rfl
```

`bind_method` defines `root` (the index), `rootBody` (the extracted body) and
the `rfl` theorems `root.signature` and `root.found` (`@[cil_code]`).
`bind_callee` also requires the parent to call that method and adds
`left.call`, the instruction at its call site (`from rootBody [k]` selects one of
several); expected bodies take the index as a parameter, so `.call left 2`
survives renumbering. `method_named "sig"`
is the bare index as a term. A missing signature lists the methods with the
same name, or every method; a duplicate lists each index; a parent that does not
call the method lists what it does call:

```text
no extracted method has signature
  System.UInt64 Examples.Overloads::Pick(System.Int64)
methods named Pick:
  [3] System.UInt64 Examples.Overloads::Pick(System.UInt64)
  [4] System.UInt32 Examples.Overloads::Pick(System.UInt32)
```

When a helper's name is not stable, bind it by call shape instead:
`bind_callee left leftBody := call 2 from rootBody [1]` binds the second call in
`rootBody` with two arguments, and emits the same theorems with the signature read
from the table. Without `[k]` there must be exactly one such call; otherwise the
error lists each site's pc and callee.

The signature is the Cecil full name, matched exactly. Resolution only locates
an index; the body is still bound by the kernel and the extraction certificate.
`bind_import` reports a missing import signature the same way, listing imports
with the same name or every import, and says when the extraction has no imports.
`Tests/MethodIdentity.lean` covers the diagnostics, and `Tests/MethodIdentity.cs`
verifies one unedited proof against two builds with different numbering.

### Loop heads and call sites

Inside a method, name positions by structure instead of by pc, so a statement
inserted elsewhere moves the label with the code (`CIL.StructuralLabels`):

```lean
import CIL.StructuralLabels

bind_loop reduce := rootBody [1]     -- the second loop head in pc order
bind_call after := step from rootBody [1]

theorem body : (rootBody.code.drop reduce).take 4 = [.local 0, .const32 3, .sub, .setLocal 0] := rfl
```

A loop head is the target of a branch at the same or a later pc. `bind_loop`
defines `reduce` and `reduce.latch`, the last pc branching back to it, and
`reduce.backEdge` checks both. `bind_call` names a `.call` to a bound method
and adds `after.call`. The `[k]` is needed only when there are several; without
it every candidate is listed rather than the first one taken:

```text
rootBody has 2 loops; select one with [i]:
  [0] head pc 3, back edge from pc 5
  [1] head pc 6, back edge from pc 7
```

Labels read the compiled layout, so a compiler that rotates a loop moves its
head; a cutpoint that must survive that, such as `Examples/Proofs/Countdown.lean`,
keeps a unique-instruction predicate. `Tests/StructuralLabels.lean` covers the
diagnostics, and `Tests/StructuralLabels.cs` verifies one unedited proof against
a build with a statement inserted before both loops.

### PDB local names and source locations

When a portable PDB matches the assembly (next to it, or embedded), extraction
also writes `Symbols.lean`, the module `ExtractedSymbols`; `Extracted.lean` is
byte-identical either way. A proof that imports it can name locals by their C#
names, resolved in the scope that contains a pc:

```lean
import ExtractedSymbols

theorem stores : sumBody.code[atWide + 1]? = some (.setLocal (local_named sum "carry" at (atWide + 1))) := rfl
```

A name used for one slot needs no `at`; a name the PDB gives two slots, such as
`carry` declared in two sibling blocks, is an error listing each slot and range
until `at pc` picks the innermost scope containing it. Compiler temporaries and
values the compiler keeps on the stack have no name and keep their index; a
missing name lists the method's named locals. Importing `ExtractedSymbols`
without a matching PDB fails verification with that reason, naming the assembly
and method. Consumer packages import it like `Extracted`, directly or through
their own modules, in `leancil verify --proof-root` and `leancil verify-batch`.
Only proofs whose imports reach it compile it, replay it and bind its hash into
their cache key, so a PDB-only change rechecks them and no symbol-free proof.

With the module imported, `cil_body` and `cil_embed` failures end with the
nearest sequence point of the actual pc they report:

```text
source of actual pc 23: Names.cs:12:9
```

Extraction errors for an unsupported instruction add `Source: Names.cs:16:21`
after the method whenever the PDB is present, imported or not. Source paths are
relative to the directory the method documents share. Without a PDB every
message is unchanged. `Tests/DebugNames.lean` covers scoping and both
diagnostics, and `Tests/DebugNames.cs` checks byte-identical extraction, an
unedited proof across an inserted local, and each message with and without a PDB;
`Tests/ConsumerSymbols.cs` covers consumer packages, batches and PDB-only changes.

### Bodies modulo dead code

A profile can make the extractor emit dead `.unsupported` blocks that shift
every later branch target, which breaks a `cil_body` equality even though
reachable behaviour is unchanged. `cil_embed` (from `CIL.Embedding.Tactic`)
proves the weaker `MethodEmbeds` relation instead: every live instruction of the
literal body appears in the extracted method at a mapped pc, with its code
targets mapped the same way and its fallthrough kept adjacent. Keep the proof
over the literal body and transport it with the lemmas in
`CIL.Safety.Embedding.Simulation`:

```lean
import CIL.Embedding.Tactic
import CIL.Safety.Embedding.Simulation

theorem bound : CIL.MethodEmbeds Extracted.program 2 (Full.fullBody Extracted.profile 9 5 7) := by cil_embed

-- A run proved over the literal body holds for the extraction with the same fuel.
example {fuel : Nat} {args : List CIL.Safety.Value} {m : CIL.Safety.Memory} {r : CIL.Safety.Memory × List CIL.Safety.Value}
    (h : CIL.Safety.invoke (Extracted.program.set 2 (Full.fullBody Extracted.profile 9 5 7)) fuel 2 args m = .ok r) :
    CIL.Safety.invoke Extracted.program fuel 2 args m = .ok r := bound.invoke h
```

An expected body can be a shared template with local flag and callee parameters.
Use `cil_embed [sse, avx, called]` when those hypotheses equate the parameters to
the extraction's concrete flags and callee indices. The tactic rewrites only the
supplied facts before alignment and unfolds local definitions; it does not infer
flag equalities from the extracted code. Relevant parameters that remain open are
rejected. The rewrite proof and the complete instruction map are kernel checked,
including branch targets and callee indices. The no-argument form still handles
closed bodies directly.

`Tests/ProfileEmbedding.lean` binds one template and one open theorem to three valid
profiles, including shifted branch targets, without restating the template body for
each profile. It also rejects unresolved flags, incorrect flag and callee values,
and a changed branch target. An irrelevant open argument may be removed by supplying
the definition that ignores it in the fact list; this is justified by reduction,
not an assumption about that argument's value.

`bound.certificate` transports an `InvocationCertificate` and
`bound.descriptors` the program's static descriptor list; `ProgramRefines.set`
composes several bound methods. Named exceptions transfer too:
`bound.raises` transports `Raises`, `bound.holds` an `OutcomeContract.Holds`
with both clauses (from `CIL.Safety.Embedding.Outcomes`), and
`Embeds.invoke_raise` states the actual fault, whose pc is the one the map
assigns in the throwing method. Other faults, including fuel exhaustion and
`.unsupported`, do not transfer. The pc map is computed outside the kernel and then checked by
it, so a wrong map is rejected, not trusted. A changed reachable instruction or
an inserted live one is reported by expected and actual pc:

```text
cil_embed: the expected body does not embed into the extracted method
method index 0
expected pc 1 maps to actual pc 1
  expected: CIL.Op.brzero 4
  renamed:  CIL.Op.brzero 6
  actual:   CIL.Op.brzero 4
  code target differs: expected target 4 maps to actual pc 6, but the actual instruction targets 4; actual pc 4 (CIL.Op.const32 0x00000009#32) is not the image of any live expected pc
```

The kernel check takes about 0.12 s for a 202-instruction body and 1.3 s for
1,414 instructions. See [docs/SOUNDNESS.md](SOUNDNESS.md#method-body-embedding)
for the exact conditions and limits; `Tests/MethodEmbedding.lean` covers both
outcomes, and `Tests/OutcomeEmbedding.lean` transfers a raising helper and its
caller across an inserted dead block, with the relocated throw pc.

An extraction can also declare locals the literal body never uses. Exact-memory embedding
covers dead locals that trail the body's own locals and are
references or spans initialized to their empty value or left unmodeled. These cover
byref, pointer, `Span<T>` and `ReadOnlySpan<T>` locals; spans require an element width
of 1, 2, 4 or 8 bytes. For those, `cil_embed` proves
`MethodEmbedsDeadLocals` instead, and the same proof covers extractions with and
without them (from `CIL.Safety.Embedding.DeadLocals`):

```lean
theorem stored_dead_embeds : MethodEmbedsDeadLocals [storedDead] 0 stored := by cil_embed

theorem stored_dead_returns (memory : Safety.Memory) (value : W32) :
    Safety.invoke [storedDead] (executionBound [stored] 0) 0 [.scalar (.i32 value)] memory =
      .ok (memory, [.scalar (.i32 value)]) :=
  stored_dead_embeds.invoke (stored_invocation memory value)
```

`.raises`, `.method_holds` and `.holds` transfer as for `MethodEmbeds`. A
numeric dead local, such as a flag only one architecture's path reads, requires the
allocation refinement below: its home shifts later allocation identities. A dead local
before a kept one also changes the kept local's operand. Span slots retain their width,
mutability and empty
or unmodeled state; padding does not create or change any allocation.

For numeric or interspersed dead locals, keep the extracted declarations and original
local indices in the expected body and use ordinary `MethodEmbeds`. Unreachable code
can still be omitted or marked `.unsupported`; declaring an unused numeric local
continues to allocate its home. This preserves the identities of later parent and
callee allocations and allows exact-memory contract transport. The int256 multiply
fixture follows this route: its scalar body retains all 22 word64 and four vector256
homes used across its architecture-specific paths. See
[Tests/RetainedNumericLocals.lean](../Tests/RetainedNumericLocals.lean) for a smaller
example with dead numeric locals on both sides of a live reference local and an
allocating child call. This route retains exact final memory and remains useful when a
postcondition names fresh references.

To omit numeric or interspersed declarations from the proof body, import
`CIL.Safety.AllocationRefinement` explicitly; `import CIL` leaves this optional proof library
unloaded. Its dependencies still undergo the normal build and kernel replay when a consumer
uses them. `LocalIndexMap.keep`, `.skip` and `.nil` describe the
retained declarations in order. `LocalDeclarations` checks matching retained kinds and
initializers and requires inserted dead declarations to be unmodeled. `MethodRenaming` checks the
target code's relocated local operands; method indices, call targets, profiles, return
metadata and static sites stay exact. `ProgramRenaming` supplies this correspondence for
every source method. The target is the extraction with the additional dead declarations.

This entry route requires `OrdinaryFrame` on both sides: `opaqueVectorLocals`, `vectorArgs`
and `parameterHomes` are empty. Retained initializers stay exact, including initialized
numeric helpers; their successful setup is derived from the actual source execution.
Local widths must fit the native range; span element widths must be 1, 2, 4 or 8.
These are explicit, checked metadata conditions, not assumed target frame-entry success.
The audited int256 Multiply body across all fourteen profiles has 22 word64 and four
vector256 unmodeled locals. Its reachable helper method4 has an initialized word64 zero
local in every profile. The full extracted programs have no opaque, vector-argument or
parameter homes; the relation preserves that helper initializer rather than treating it
as unmodeled.

Starting from the same well-formed memory with bounded static bindings,
`ProgramRenaming.invoke_scalars` transfers a successful checked invocation with the same
fuel and exact scalar results. Its final memories satisfy `MemoryBelow` at the initial
allocation counter. `invoke_confined` also carries a `MemoryBelow` preservation claim from
the initial memory to the target's final memory. `ProgramRenaming.raises` transfers a
named exception and additionally requires valid initial arguments. These theorems use
the proved complete dispatcher internally. The allocation relation extends through
local setup, nested calls, constructors, static allocation and `stackAlloc`; frame
ownership and expiry remain checked.

`MethodContract.Holds.of_allocationRenaming` transfers the original complete contract,
including its precondition and footprint. Supply proofs that the precondition establishes
well-formed memory and bounded static bindings, that the contract encodes scalar outputs,
and that its postcondition is preserved by `MemoryBelow` on the initial caller prefix.
The adapter derives confinement from the actual paired executions; it does not replace
the contract with a weaker one.

This is not exact-memory transport: extra homes change counters and fresh references.
Arbitrary reference results and postconditions naming fresh allocations need a statement
modulo the allocation relation. The existing `MethodEmbedsDeadLocals` tactic continues to
handle its exact-memory subset. See
[Tests/AllocationExecutionRenaming.lean](../Tests/AllocationExecutionRenaming.lean) for
two live numeric locals interspersed with three dead ones, an initialized nested helper followed by
dynamic allocation, exact scalar results, caller-prefix preservation and a named exception.

### Generated profile templates

Create ordinary extractions for the profiles your proof supports, then combine them:

```sh
leancil extract Dispatch.dll 'Dispatch::Choose(uint,uint)' scalar scalar
leancil extract Dispatch.dll 'Dispatch::Choose(uint,uint)' sse42 x64-sse42
leancil extract Dispatch.dll 'Dispatch::Choose(uint,uint)' v3 x64-v3
leancil templates shared scalar sse42 v3
```

The command reruns exact extraction checking for every input and requires the same
assembly bytes. `shared/Templates.lean` defines each method once, with a profile parameter,
parameters for the feature flags it reads, and managed callee indices keyed by full method
identity. Every original IL instruction keeps its pc. Conditional instructions and excluded
paths become `if` expressions and unsupported padding; `cil_instruction_equations` generates
kernel-checked equations for every pc.

`TemplateBindings0.lean`, `TemplateBindings1.lean`, and so on each import `Extracted` and
`Templates`. Each binding proves `Extracted.program[i]? = some (Templates.methodN ...)`
by `rfl`, including all metadata and callee indices. Compile a binding only against its
corresponding extraction, recorded in `templates.json`. Add the shared module and selected
binding module to your proof package, import that binding from the consumer proof, and use
ordinary `leancil verify` with that extraction and proof package. The templates command
generates proof source; it does not replace Lean checking or verification of the extraction.

Only the input profiles receive extraction bindings. Unselected combinations of observed
flags produce unsupported instructions, and no correctness claim about another extraction
follows from generating a template. The full profile remains an explicit parameter; a
behavioral proof must relate its feature fields to the flag arguments it uses. Profiles
that produce different metadata, different instruction counts, or different instructions
under identical observed flags are rejected. Static-site metadata, imported callee slots
and the model's `newVector256` constructor form are currently unsupported in template generation.

`Tests/ProfileTemplates.cs` compiles a real AVX2/SSE4.2 dispatch helper and checks one
shared proof from `Tests/ProfileTemplatesProof.lean` against three profiles. A fourth
extraction changes the managed callee numbering through a wrapper entry point. The suite
replays the generated equations, extraction certificates, bindings and consumer proofs in
the kernel, and rejects changed flag values, callees, branch targets, instruction equations,
stale extraction source and incompatible profile-dependent parameter homes.

### Instruction equations for parametric bodies

A body written once for every profile takes its feature flags and callee
indices as parameters and keeps each feature-dependent instruction as an `if`,
padding the other profile's side with `.unsupported` so every profile has the
same pcs. `cil_instruction_equations` (from `CIL.InstructionEquations`) states
one `@[cil_code ↓]` equation per pc for such a body, the same
`code[pc]? = some op` equations the extractor emits for its own methods, so a
lookup rewrites by one equation instead of unfolding the body:

```lean
import CIL.InstructionEquations
import CIL.Safety.SymbolicExecution

abbrev unreachable : CIL.Op := .unsupported "Unreachable under selected profile"

def body (sse42 avx2 : Bool) (callee : Nat) : CIL.Method :=
  { profile := { sse42, avx2 }, returnsValue := true, locals := [], code := [
    .feature .avx2, .brzero 4,
    if avx2 then .call callee 0 else unreachable,
    if avx2 then .ret else unreachable,
    if avx2 then unreachable else .ret] }

cil_instruction_equations body

-- body_instruction2 (sse42 avx2 : Bool) (callee : Nat) :
--   (body sse42 avx2 callee).code[2]? = some (if avx2 = true then .call callee 0 else unreachable)
-- cil_lookup fetches through the equation and decides the `if` from the fact.
example (sse42 avx2 : Bool) (callee : Nat) (wide : avx2 = true) :
    ∃ op, (body sse42 avx2 callee).code[2]? = some op ∧ op = .call callee 0 :=
  ⟨_, by cil_lookup [wide], by with_reducible rfl⟩
```

A body whose code length depends on a parameter, such as an `if` around a
whole block, is rejected with the first pc that is not determined. Only the
kernel checks the equations: 100 instructions take about 0.1 s, 400 take 2.4 s
and 1,500 take 32 s, growing with the square of the length like the extractor's
own equations, and about eight times faster than writing each `:= rfl` by hand.
`Tests/InstructionEquations.lean` covers lookups on symbolic flags and on
concrete profiles, with the body sealed so only the equations can fetch, and a
`cil_checked_steps` run decided by a fact about a symbolic flag.
